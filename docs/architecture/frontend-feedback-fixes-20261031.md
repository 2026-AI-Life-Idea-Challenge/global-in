# 프론트 피드백 보완 — MJfront

## 상담 중복 질문

상담 본문과 `follow_up_questions`가 같은 질문을 담고 있었고 두 영역에서 반복 표시했다. 본문에 이미 있는 질문은 아래에서 다시 표시하지 않으며, 별도의 추가 질문은 유지한다.

## 422가 500으로 보이던 오류

실행 중인 백엔드로 재현했다. 상담 응답의 `UserProfile`에는 `application_date`, 보험·참여 이력 등의 내부 필드가 null 기본값으로 포함되지만, 다음 요청의 `ProfileUpdateRequest`는 그 필드를 허용하지 않아 422를 반환했다. 프론트 프록시는 이를 예외로 바꿔 500으로 응답했다.

- 입력에 없는 것과 동등한 응답 전용 null 필드는 요청 검증 전에 제거한다.
- 알 수 없는 non-null 필드는 여전히 거부한다. 사용자 정보를 임의로 버리거나 판정 값으로 신뢰하지 않는다.
- 프론트는 입력 오류를 422로 유지하고 프로필 입력 안내를 표시한다. 백엔드의 원문 입력값이나 상세 오류를 노출하지 않는다.
- 실제 서버의 검증 전용 요청에서 위 프로필 오류들이 제거된 것을 확인했다. 빈 메시지는 의도적으로 남겨 모델 호출 없이 검증했다.

## 데이터셋 기반 상세 정보

- `GET /consult/catalog/{target_id}`와 서버 프록시를 추가했다. 기존 내부 API 키 인증을 사용한다.
- 현재 대상에 연결된 활성 문서·개정·청크를 읽기 전용으로 조회한다.
- 개요에 요건 목차를 표시하고, 기존 대상·조건 카드에서 저장된 본문·예외·공식 출처·확인일·적용 기간을 표시한다. 본문은 AI로 새로 생성하거나 수치·조건을 바꿔 쓰지 않는다.
- 52개 대상 모두 활성 본문이 있음을 확인했다. 호주 186 Direct Entry는 본문 12건·공식 출처 12건을 확인했다.
- 상세 ID의 중복 인코딩으로 자료를 못 찾던 문제도 수정했다.
- 데스크톱 카드 배치는 유지한다. 작은 화면에서 두 열이 겹쳐 글자가 한 글자씩 줄바꿈되는 문제만 한 열로 보정했다.

## 플랜 화면

과거 원본 플랜은 빈 상태 화면만 구현되어 있었다. 채워진 상태를 완성된 원본 디자인으로 복원한 것은 아니었다. 기능 추가 때 스타일 없이 넣었던 컨트롤에 기존 색상·테두리·버튼 규격을 적용했다.

상단의 긴 프로그램명을 줄줄이 출력하지 않고 각 항목의 메타 정보에서 프로그램별 진행 개수를 표시한다. 수정/삭제 버튼과 추가/편집 입력 폼을 구분하고 좁은 화면에서 넘치지 않도록 했다. 전체 레이아웃, 로고, 전역 CSS 파일과 기존 빈 화면은 변경하지 않는다.

## 검증

- Python 270개 + 223개 subtests 통과(기존 경고 4개).
- 프록시/SSR 13개, Chromium 기능 검사 28개 통과. 합성 API 사용.
- TypeScript 및 webpack 빌드 통과. 변경 화면 lint 오류 0개, 기존 이미지 경고 1개.
- 플랜 데스크톱·모바일 캡처 확인.
- 정책 DB 쓰기·임베딩 생성·유료 모델 호출 없음. 실제 데이터 조회와 422 검증 전용 요청은 읽기/검증 범위다.
