# 기획·에이전트 범위 대비 데이터 준비 상태

## 결론

에이전트 골격 개발과 검증된 일부 근거의 시험 임베딩은 진행할 수 있다. 현재 데이터가 기획 전체를 충족한 최종 불변본이라고 보고 전량 임베딩하는 것은 이르다. 570개 문구의 내부 검토 완료와 비자·국내외 지원제도·실행 가능한 규칙·체크리스트 전체 구축 완료는 다르다. 앞선 완료 보고는 그 범위를 충분히 구분하지 않았다.

이 대조는 사용자의 초기 기획서와 5개 에이전트 구상, 실제 공유 ZIP의 DB 스냅샷, app/models/program.py, scripts/init_db.sql 및 app/rules·app/retrieval의 구현 파일 목록을 기준으로 한다. 현재 DB를 변경하거나 임베딩을 실행하지 않았다.

## 확인한 상태

| 범위 | 확인 결과 | 다음 보완 |
|---|---|---|
| 비자·체류 프로그램 | 40개, 5개국×3개 상위 분류가 등재됨 | 등재만으로 15개 경로의 자격·서류·일정 깊이가 같다고 판단하지 않음 |
| 정책 검토 | 590개 중 내부 검토 문구570개, 과거 공고20개 | 공식 원문·검토자 해석을 검색에서 구분하고 승인 범위를 유지 |
| 원문 근거 | evidence1241개 | 모두를 임베딩 승인한 것은 아님. 중복·표의 행/열 맥락·문서 버전별 청킹 점검 |
| 한국 측 지원제도 | KR_SUPPORT_* 및 KR_US_*7개 | 저장된 지원 요약과 검토570개의 범위를 혼동하지 않음. 자격·기간·증빙 검증 필요 |
| 목적지 국가 지원제도 | 별도 목적지 측 지원제도로 식별된 레코드는 위7개 목록에서 확인되지 않음 | 5개국의 실제 제도 존재·한국인 적용·신청 상태를 각각 확인해 추가 |
| 공통 모델 | 프로그램·지원제도 분리, 가변 metadata 존재 | 발행국/목적지국, 국적/거주지/신청지역, 정보 유형·기관·각종 날짜를 일관되게 정의 |
| 비자와 지원제도의 연결 | 현재 초기 테이블에 관계 전용 테이블 없음 | 여러 경로와 연결 가능한 관계 및 근거를 정의 |
| 자격 검토 | 정책 문구와 Rule Evaluator 설계 README 존재 | 실제 evaluator 구현과 요건·AND/OR·예외·judgeability 데이터 구축 필요 |
| 임베딩 저장 | evidence_id·model·vector 기반 초기 테이블 | 청크 ID·내용 해시·원문/검토 버전·메타데이터 필터·활성/보관 상태의 버전 계약 확정 |

현재 evidence는 program_id를 참조한다. 지원제도 근거도 같은 검증·검색 체계에 넣으려면 지원 대상 연결 모델을 함께 정해야 한다. 하나의 country 필드만으로 한국 발행·독일 목적지 등을 표현하지 않는다.

## 지금 고정할 최소 계약

- Program과 SupportProgram의 고유 ID 및 둘 사이의 다대다 연결.
- 발행 기관·발행국·목적지국, 적용 국적·거주지·신청지역, 주제·원문 유형.
- 공식 원문·검토자 해석의 구분. 기관 재량·미해소 충돌은 자동 PASS로 변환하지 않음.
- 자격 충족 상태와 접수 가능 상태(OPEN/CLOSED/UPCOMING/UNKNOWN)를 분리.
- 공식 게시/업데이트일, 시행/적용 기간, 시스템 확인일을 분리하고 미확인은 NULL/UNKNOWN으로 보존.
- 문서·문구·청크 버전, content_hash, embedding 입력 텍스트, 모델·차원과 검색 필터 계약.

## 권장 진행 순서

1. 위 계약과 현재 데이터의 누락 범위를 정하고 개발용 v1 스냅샷을 고정한다.
2. 원문 근거 중심으로 소량 청킹·시험 임베딩 후 검색·출처·적용 대상 필터를 검증한다. 검토 문구를 공식 원문인 것처럼 임베딩하지 않는다.
3. 프로필·의도·라우팅·Missing Information·검색 인터페이스 등 에이전트 골격은 병행한다.
4. 국내외 지원제도와 구조화 요건·체크리스트를 보완하고 국가·경로별 시나리오를 검사한다.
5. 임베딩 허용 대상을 확정해 본 작업을 실행한다. 현재 approved_for_embedding=false를 무시하고 전체 자료를 실행하지 않는다.

데이터는 이후에도 보완·정정될 수 있다. 입력 텍스트가 같은 메타데이터 수정에는 보통 재임베딩이 필요 없고, 텍스트 변경·추가는 해당 청크만 갱신한다. 모델·차원 또는 청킹 기준을 바꾸면 더 넓은 재생성이 필요할 수 있다. 정책 자동 갱신 기능을 지금 구현하지 않아도 버전·해시 기반의 수동 갱신 구조는 먼저 둘 수 있다.
